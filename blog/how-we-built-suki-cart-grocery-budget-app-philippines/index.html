How we built Suki Cart, a grocery budget app for Filipino shoppers, and the row that only broke on a real screen

By Jamz Jamorol, founder of JTL Growth, Metro Manila, Philippines · 27 November 2026

Suki Cart is an iPhone grocery budget app: type each price as it goes in the cart and see what is left. Venice, our AI operator, built it and I tested it. Our web tests passed while one row sat half hidden under the bottom of an iPhone 17 screen, so a tap hit nothing. That one miss changed how we test every app.

What Suki Cart is

You add items to the cart, the total grows in your head, and at the counter it is more than you brought. Then you choose what to put back while the line waits. Suki Cart keeps the running total for you. You type each price as it goes in the cart and see what is left of your budget before you reach the counter.

It counts per kilo, quantity and buy-one-take-one prices, and estimates senior citizen and PWD discounts. If you go over budget, Suki, the cart buddy, shows what to take out, and you decide. You can set a budget until payday, share a Bahay code so a family sees the month's total, and switch between Filipino and English. It is free to download.

Venice, our AI operator, built the app and its tests, and I review it on my iPhone through TestFlight. It is written with Expo, so the same code runs as a web build and a native iPhone app. That detail matters for what broke.

The moment it went wrong

Our first tests were web walks. A script opens the web build, adds items, starts a trip, taps Backup, and checks what happens. They ran in dark and light and they passed every time.

Then we ran the app natively on an iPhone 17 simulator. On the start screen, a row with the Price, Backup and Pro buttons sat half under the bottom edge of the screen. We tried a tap and it hit nothing.

The odd part was what the tools said. The native UI test tool, Maestro, reported that clipped row as 100 percent visible. The tap landed on empty space anyway.

What we tried first, and why it did not hold

The web walks were not wrong. They were blind in one specific way. The browser test tool scrolls an element into view before it clicks it, so a row half hidden by the screen edge gets scrolled up and clicked fine. A person on a real phone does not get that help.

The native tool had a different blind spot. It trusted the element tree, which listed the row as present and visible. We only saw the clipped row by looking at the screenshot.

We also learned about a second, quieter problem on the way. The simulator that was already booted on the Mac was shared with other sessions. In the middle of one run, another app took over the screen. So the native lane now builds and runs on its own simulator, named Suki QA, and never touches the shared one.

The real fix

The commit on 2026-10-21 moved the Price, Backup and Pro row under the scroll view, so it is pinned and never sits half under the edge. We rebuilt a release build and checked that Backup opens on the first tap, then re-ran the web walks in dark and light.

That same pass found a second bug that no web walk could have caught. After a backup, the app said Saved even when the person cancelled the share sheet, because the share library reports the same result for saved and cancelled. A backup that says saved when nothing was saved is the worst kind of wrong. Save now opens the folder picker, writes the file, reads it back, and only then says where it was saved. A separate Send option, which cannot know the outcome, records no date and says only: if you saved it, your trips are safe.

The check that guards it now

Native QA is now its own lane. One script builds the app on the Suki QA simulator and runs Maestro flows for the price-tag scan, backup, buying Pro and restoring it, plus a StoreKit pass for purchases. The lane also reads the price tags with Apple's Vision framework, and a planted wrong price fails the test, so we know the check can fail. After any layout change to the start screen we run the flows and look at the screenshot with our own eyes. At that commit, 162 tests passed.

A related catch the next day: builds 1 to 5 went to TestFlight with Expo's template icon, a blue letter A, because every size check passed and none looked at the picture. Apple rejects starter icons. The store check script now hashes the 1024 pixel icon against known templates and fails on a match.

What we would do differently

We would run the native pass from the first week. A web build is a fine place to test logic, but a layout that has to fit a real iPhone screen needs a real iPhone screen, and a green web walk says nothing about it.

We would also never accept a saved message that is not backed by a read-back, and we would look at the picture, not just the numbers, before any upload. Suki Cart 1.0 is on the App Store now, and it was a better app for the row that failed.
