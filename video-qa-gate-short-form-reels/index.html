Every Catch Becomes a Check: The QA Gate Behind Our Short-Form Reels

We make short-form b-roll reels for a client's clinic. Two reviewers caught problems that our own checks missed. We turned each catch into a script that runs on every render. The same mistake can no longer reach a reviewer twice.

The problem

A reel is a few seconds of footage with text on top. We build many of them, fast. Our first review step was simple: look at three still frames per reel, then send it.

That step passed a draft that looked fine in stills. In motion it stuttered. Our owner watched it and said it seemed to "stop, stop". He was right.

What broke

The source clip held about 140 duplicated frames. Our short slices landed on them, so the picture froze for a beat, then moved. The same shot also showed up in more than one reel. Stills cannot show either problem. A still is one frame. A stutter is a pattern over time.

What we tried

First, we promised to watch every render before sending. That is a habit, not a fix. Habits fail on busy days, so we wrote a gate.

The gate reads each video with ffmpeg and runs these checks:

  • Duplicate frames. The mpdecimate filter drops frames that match the one before. More than two in a row fails the video, and the gate prints the times so we can move the cut.
  • Held stills. Any frame held longer than 1.5 seconds fails.
  • Black frames. The blackdetect filter flags any black run of 0.1 seconds or more.
  • Shot reuse. We sample each video at 2 frames a second, shrink the frames, and compare them on a 4 by 4 grid of tiles. A different text overlay on a few tiles does not hide a match. A matching run of one second or more fails the batch.
  • Contact sheet. The gate also builds a 6 frames a second sheet for a human to read.

The reuse check needs the whole batch in one call. That detail matters, because the repeats we saw were across reels, not inside one.

The gate caught our bad first draft. We also wrote regression tests for its cut-detection rule, so a later tweak cannot quietly loosen it.

The second catch

A team editor then pointed out that our on-screen text sat on top of a person's face on some shots. The text had one fixed position. On some shots, that position was a face.

We wrote a second script. It detects faces shot by shot with a small ONNX face model, at 6 frames a second. It also tries the frame turned 90, 180 and 270 degrees, because people lie down and cameras rotate. Each face is grown by 15 percent, and the text box keeps 40 pixels clear of it.

It then tries the text box at every 20 pixel height inside the safe zone for the Reels app. If one height works for every shot, it uses that. If not, each shot gets the nearest free height to the last one, so the box jumps as little as possible. If any shot has no free height, the script exits with an error.

The margin came from a later miss. A face still sat under the text at a plain detection score with no margin. We added the margin and the sideways frames after that.

The check that guards it now

Both scripts run on every render, before anything goes to a reviewer. A pass writes one line to a ledger, so any send can be traced to its gate run. A failed video does not go out.

The gate cannot watch for us. It says so in its own notes: someone still reads the contact sheets. What it removes is the repeat error.

What we would do differently

  • Write the gate before the first batch, not after the first complaint. A video has failure modes that stills hide, and that was knowable.
  • Run face detection on the clean video before text goes on. We now do, and we should have started there.
  • Put every new reviewer catch into the same gate on the day it happens, with a test that fails on the old mistake.

The lesson

Review is expensive and people forget. A catch that stays in someone's memory will come back. A catch that becomes a check runs every time, costs nothing, and gets better with each miss.
